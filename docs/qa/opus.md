### 가장 중요한 문제

**서버 키워드 위기 검사가 받침이 붙는 활용형을 놓친다.** 규칙 목록에 있는 표현인데도 걸리지 않는다. 예: "죽어버릴까", "죽어버린다", "죽는 게 낫겠다", "인생 끝낼래", "사라져버릴래". 규칙은 완성된 글자(음절) 단위로 비교하는데, "버리"와 "버릴", "나"와 "낫"은 서로 다른 글자이기 때문이다. 여기에 목록에 없는 흔한 표현("그만 살고 싶다", "더 이상 살 이유가 없어" 등)까지 더하면, 독립적으로 만든 위기 문장 45개 중 **29개(64%)만** 감지했다. PRD S2 목표(100%)에 못 미친다. AI가 두 모델 모두 실패하면 이 문장들에는 상담 연락처가 전혀 나오지 않는다(S3, F5 완료 조건 4).

## 2. 발견한 문제 (심각한 순)

### [높음] 위기 키워드 검사가 받침 붙은 활용형을 놓친다

- **위치**: `src/lib/ai/crisis.ts:193` (`NOT_WORD_PATTERN`), `:208-218` (`detectCrisis`), 규칙 예 `:49` `"죽어버리"`, `:53` `"죽는게나"`
- **문제**: 규칙은 "어간만 적어 활용형을 한꺼번에 잡는다"는 설계다(파일 주석 76행 부근). 그런데 비교는 완성형 음절 문자열의 `includes`라서, 규칙의 마지막 글자에 받침이 붙으면 다른 글자가 되어 걸리지 않는다.
  - `"죽어버리"`는 "죽어버**릴**까", "죽어버**린**다", "죽어 버**릴** 거야"를 못 잡는다.
  - `"죽는게나"`는 "죽는 게 **낫**다", "죽는 게 **낫**겠다"를 못 잡는다. "죽는 게 나아"만 잡는다.
  - `"사라져버리"`, `"없어져버리"`, `"끝내버리"`도 같은 이유로 "~버릴래/버릴까"를 못 잡는다.
  - `"생을끝내"`, `"삶을끝내"`, `"인생끝내"`는 "인생 끝**낼**래", "삶을 끝**낼**래", "생을 끝**낼**까"를 못 잡는다.
- **재현 방법** (재현함): `detectCrisis`를 node로 직접 실행했다.
  - `false`: "죽어버릴까", "죽어버릴래", "죽어 버릴 거야", "죽어버린다", "죽는 게 낫다", "죽는 게 낫겠다", "사라져버릴래", "사라져버릴까", "없어져버릴래", "끝내버릴까", "인생 끝낼래", "삶을 끝낼래", "생을 끝낼까"
  - `true`: "죽어버리고 싶다", "죽는 게 나아"
- **영향**: AI가 두 모델 모두 실패하거나 AI도 위기로 보지 않으면 상담 연락처 상자가 나오지 않는다. PRD S2·S3, F5 완료 조건 4·8에 못 미친다.
- **고칠 방법 제안**: 긴 표현(`CRISIS_PHRASES`)을 비교할 때 일기와 규칙을 모두 NFD(초성·중성·종성 자모)로 풀어서 비교한다. 이렇게 하면 "버리"(ㅂㅓㄹㅣ)가 "버릴"(ㅂㅓㄹㅣㄹ)의 앞부분과 맞는다. 이때 `NOT_WORD_PATTERN`이 자모 범위(`\u1100-\u11FF`)를 지우지 않게 고쳐야 한다. 메모리 안에서 시제품으로 돌려 보니 위 예 중 "죽어버릴까", "죽어버린다", "죽는 게 낫겠다", "사라져버릴래", "끝내버릴까", "인생 끝낼래"가 모두 걸렸다. 일상 문장 "오늘 친구와 웃었다", "배고파 죽겠다", "죽을 만큼 맛있었다"는 새로 걸리지 않았다. 고친 뒤에는 4절의 위기·일상·관용 목록을 `crisis.test.ts`에 회귀 시험으로 넣는다.
- **확인 수준**: 재현함

### [중간] 흔한 위기 표현이 규칙 목록에 없고, 2글자 단어는 띄어쓰기·문장부호로 피해 간다

- **위치**: `src/lib/ai/crisis.ts:35` (`CRISIS_SHORT_KEYWORDS`), `:214` (짧은 단어는 띄어쓰기를 둔 글에서만 비교), 규칙 목록 `:38-171`
- **문제**:

- **재현 방법** (재현함): 위 문장을 `detectCrisis`에 넣으면 모두 `isCrisis: false`다.
- **고칠 방법 제안**: "그만살고싶", "살이유", "없어지는게나", "없어져도", "영원히잠들", "잠들고싶", "죽어마땅", "떨어지고싶", "몸을긋", "뛰어내리"(자모 비교와 함께), "포기하고싶", "못버티" 등을 넣을지 검토한다. 짧은 단어는 "글자 사이에 공백·문장부호 한 개만 끼운 경우"(예: 정규식 `자[\s.\-·]?살`)도 보게 한다. 넣을수록 오탐이 늘어나므로 다음 항목의 기준 결정과 함께 정한다. PRD 방침은 "놓치는 것보다 잘못 띄우는 쪽"이다.

### [중간] 위기일 때 "밝은 응원 문구 없음"을 서버가 검사하지 않는다

- **위치**: `src/lib/ai/schema.ts:106` (`modelAnalysisSchema`), `src/lib/ai/index.ts:82-89`, `src/lib/ai/prompts.ts:68`, `:70`
- **문제**: PRD F5 완료 조건 7("위기일 때 공감 메시지에는 밝은 응원 문구가 없다")을 프롬프트로만 지시한다. 모델이 지시를 어기고 "힘내요", "파이팅", "다 잘될 거예요"를 쓰거나 감정을 "기쁨"·"평온"으로 고르더라도, 응답은 검증을 통과해 위기 사용자에게 그대로 보인다. 특히 키워드는 위기인데 모델은 위기가 아니라고 본 경우(`isCrisis: false`), 모델은 평소 말투로 쓰게 된다. 그래도 최종 `isCrisis`는 OR로 true가 되므로 연락처 상자 아래에 밝은 문구가 나올 수 있다.
- **재현 방법**: 실제 모델 호출이 금지라 재현하지 못했다. 검사 코드가 없다는 것은 코드로 확인했다.
- **고칠 방법 제안**: `index.ts`에서 최종 `isCrisis`가 true일 때 공감 메시지에 금지 문구 목록(프롬프트 68행과 같은 목록)이 있거나 감정이 기쁨·평온이면, 그 응답을 실패로 보고 다음 모델로 넘긴다. 또는 위기 전용 고정 문구로 바꾼다. 금지 문구 목록은 `prompts.ts`와 한곳에서 함께 관리한다.
- **확인 수준**: 가능성 (검사 코드가 없는 것은 코드로 확인)

### [낮음] 보이지 않는 글자만 있는 일기가 저장된다

- **위치**: `src/app/api/_lib/validation.ts:41` (`value.trim()`), `src/lib/client/validation.ts:25`, `db/migrations/001_create_diary_schema.sql:37`
- **문제**: JS의 `trim()`은 너비 0 공백(U+200B), 너비 0 연결자(U+200D), 한글 채움 문자(U+3164)를 지우지 않는다. 그래서 화면에는 빈칸으로 보이는 일기가 1자로 저장된다. DB CHECK의 `\s`도 이 글자들을 공백으로 보지 않을 가능성이 있다(DB 시험이 금지라 확인 못함). PRD F2 완료 조건 2의 취지(공백뿐인 글은 저장하지 않음)와 어긋난다.
- **재현 방법** (재현함): `parseCreateBody({content:"\u200B"})`, `"\u200D"`, `"\u3164"`가 모두 `ok`(1자)다. 화면 검사 `validateDiaryContent`도 `ok`다.
- **고칠 방법 제안**: 서버와 화면 모두, 보이지 않는 글자를 지운 결과가 비어 있으면 `empty`로 본다. 지우는 글자 범위는 `crisis.ts`의 `INVISIBLE_PATTERN`과 U+3164, U+115F, U+1160이다.
- **확인 수준**: 재현함 (검증 함수 단위)

### [낮음] NUL 문자가 든 글을 화면은 통과시키고, 서버는 "요청 형식이 올바르지 않아요"로 막는다

### 2. 입력 경계값

서버 `parseCreateBody`·`parseJsonText`·`parseListQuery`와 화면 `validateDiaryContent`를 node로 직접 실행했다(5절).

- 빈 값, 공백, 줄바꿈·탭, U+3000, NBSP: 모두 `empty`
- 200자 통과, 201자 `too_long`. 앞뒤 공백을 포함해 200자인 글은 공백을 지운 뒤 200자로 통과
- 이모지 200개 통과, 201개 `too_long`
- HTML 문자열은 그대로 저장된다. 화면은 React 기본 출력만 쓴다(`dangerouslySetInnerHTML` 0건).
- 문자열이 아닌 `content`, `null`, 배열, `{}`, JSON 아님, 64KB 초과: 모두 `invalid_type`
- `limit` 0·51·빈 값·1.5·-1·0050은 400. 1과 50은 통과
- `cursor` 빈 값·`abc`·존재하지 않는 날짜(2월 31일)는 400
- id 검사: 대문자 uuid 통과. 하이픈 없는 값과 `' OR 1=1 --`는 거부되어 404
- 문제: 보이지 않는 글자만 있는 글 저장, 화면의 NUL 미검사, 합성 이모지 글자 수 (2절 낮음)
- 확인 못함: 실제 화면에 입력해 보기 (로그인 필요)
