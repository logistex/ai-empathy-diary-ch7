# 4단계 QA 모델 비교 (Haiku vs Opus)

- 날짜: 2026-11-05
- 대상 커밋: `e8acfd1` (main)
- 비교한 보고서: [haiku.md](haiku.md), [opus.md](opus.md)
- 조건: 두 모델 모두 `qa-engineer` 에이전트로, `docs/PLAN.md` 4단계 점검 목록 1~8과 같은 금지 조건(파일·DB 변경 금지, 실제 AI 호출 금지, 로그인 흉내 금지, `.env*` 열람 금지)에서 검사하고 보고만 했다. Opus는 Haiku 보고서를 읽지 않고 독립적으로 검사했다.

## 1. 건수 비교

| 심각도 | Haiku | Opus |
|---|---|---|
| 높음 | 1 | 1 |
| 중간 | 2 | 3 |
| 낮음 | 9 | 9 (보고서 기준) |
| **합계** | **12** | **13** |
| 위기 문장 시험 수 | 약 25개 | 136개 (위기 45, 일상 33, 관용 18, 활용형 30, 우회 10) |

Opus의 낮음 9건은 보고서에 적힌 숫자다. 실제 낮음 제목은 8개이고 그중 하나가 4건을 묶은 항목이라, 하나씩 세면 낮음 11건, 전체 15건이다.

## 2. 문제별 비교

| 문제 | 종류 | Haiku | Opus |
|---|---|---|---|
| 위기 키워드: "힘들어 죽을 것 같다" 놓침 | 위기 감지 | **높음** | 못 찾음 (비슷한 "피곤해 죽을 것 같다"를 관용 표현으로 보고 정상 처리) |
| 위기 키워드: 받침 붙은 활용형 놓침 ("죽어버릴까", "죽는 게 낫겠다", "인생 끝낼래") | 위기 감지 | 못 찾음 | **높음** |
| 위기 어휘 누락, "자 살"·"자.살" 같은 띄어쓰기 우회 | 위기 감지 | 못 찾음 | 중간 |
| 일상 문장 오탐 (사용자 기준 결정 필요) | 위기 감지 | 중간 (6개 중 4개) | 중간 (33개 중 15개, 관용 18개 중 6개) |
| 위기일 때 밝은 응원 문구를 서버가 검사 안 함 | AI 출력 검증 | 못 찾음 | 중간 |
| 로그아웃 후 뒤로 가기로 기록이 보일 가능성 | 권한·화면 | **중간** (bfcache) | 낮음 (`cacheComponents`) |
| 공감 메시지 검증이 PRD보다 느슨함 | AI 출력 검증 | 낮음 | 낮음 (+ 한글 1글자만 있어도 한국어로 봄) |
| NUL 문자: 화면은 통과, 서버는 거절 | 입력 검증 | 낮음 | 낮음 |
| 보이지 않는 글자만 있는 글이 저장됨 | 입력 검증 | 낮음 (U+200B) | 낮음 (U+200B·200D·3164) |
| 결합 이모지를 여러 자로 셈 | 입력 검증 | 낮음 | 낮음 |
| 본문 크기를 다 읽은 뒤 검사 | 보안 | 낮음 | 낮음 (묶음) |
| 보안 헤더 없음 | 보안 | 낮음 | 낮음 (묶음, + `X-Powered-By`) |
| 입력창에서 201자부터 막지 않음 | 화면 | 낮음 | 못 찾음 |
| AI 응답에 `isCrisis`가 없으면 false로 처리 | 위기 감지 | 낮음 | 못 찾음 |
| 재시도 때 같은 일기가 두 번 저장될 가능성 | 데이터 | 낮음 | 못 찾음 |
| 저장 중 버튼 글자 대비 2.71:1 | 접근성 | 못 찾음 (비활성이라 예외로 봄) | 낮음 |
| 로그인 후 `callbackUrl`을 쓰지 않음 | 화면 흐름 | 못 찾음 | 낮음 |
| 날짜 묶기가 한국 시간으로 고정 | 문서 불일치 | 못 찾음 | 낮음 (묶음) |
| 저장 중 401이면 쓰던 글이 사라짐 | 화면 | 못 찾음 | 낮음 (묶음) |

**겹치는 정도**: 9개는 두 모델이 다 찾았고, 4개는 Haiku만, 10개는 Opus만 찾았다.

## 3. 해석

- **가장 큰 차이는 높음 문제가 서로 다르다는 점이다.** 둘 다 "위기 키워드가 위기 문장을 놓친다"는 같은 영역이지만 원인이 다르다.
  - Haiku는 "죽을 것 같다" 계열 규칙이 없는 것을 찾았다.
  - Opus는 글자 단위로 비교해서 받침이 붙으면 못 잡는 구조 문제를 찾았다.
  - 메인 Claude가 `detectCrisis`를 직접 다시 실행해 보니 두 문제 모두 사실이었다. "힘들어 죽을 것 같다", "죽어버릴까", "죽는 게 낫겠다", "인생 끝낼래"가 모두 `false`였다. 둘 다 고쳐야 한다.
- **Opus는 폭이 넓었다.** 위기 문장을 약 5배 더 시험했고, Haiku가 보지 못한 문제를 찾았다(밝은 문구 미검사, 띄어쓰기 우회, `callbackUrl`, 버튼 대비 등).
  - 대신 Haiku의 "죽을 것 같다"는 놓쳤다. Haiku는 정해진 필수 문장 목록과 `crisis.test.ts:135`의 "4단계에서 재검토" 기록을 따라가서 이것을 찾았다.
- **Haiku만 찾은 것은 주로 동작 흐름 쪽이다.** 중복 저장, `isCrisis` 누락 처리, 입력 단계의 글자 수 제한이 그렇다.
- **심각도는 대체로 같았다.** 다른 곳은 뒤로 가기 문제 하나로, Haiku는 중간, Opus는 낮음으로 매겼다.
- **규칙 준수**: Opus는 `.env` 실제 값 대조(`node --env-file=.env`)와 `cat .env.example`을 시도했다. 둘 다 권한 단계에서 막혀 값은 노출되지 않았다. Haiku 보고서에는 이런 시도 기록이 없다.
- **비용**: Opus는 약 17분, 도구 호출 44회, 약 21만 토큰을 썼다. Haiku 쪽 수치는 기록이 없어 비교하지 못했다.

## 4. 결론

두 보고서는 서로를 보완한다. 4단계 수정 목록은 두 보고서를 합쳐 만든다. 특히 높음 2건(죽을 것 같다 계열 누락, 받침 활용형 누락)은 위기 키워드 규칙을 고칠 때 함께 처리하고, 두 보고서의 위기·일상·관용 문장을 `crisis.test.ts` 회귀 시험에 넣는다.
