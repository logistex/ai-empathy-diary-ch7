## 1. 개요

### 1.1 한 줄 설명

오늘 있었던 일을 한 줄로 쓰면 AI가 감정을 분석하고, 공감하며 위로해 주는 일기 앱.

### 1.2 배경

일기를 길게 쓰는 일은 부담스럽다. 한 줄만 써도 되고, 쓴 뒤에 따뜻한 반응이 돌아오면 꾸준히 쓰기가 쉬워진다. 이 앱은 구글 계정으로 로그인한 사용자가 자기만 볼 수 있는 일기장에 한 줄을 남기고, AI의 공감 메시지를 받는 경험을 만든다.

### 1.3 해결하려는 문제

| 문제 | 이 제품의 답 |
|---|---|
| 일기를 길게 쓰기 부담스러워 금방 그만둔다 | 한 줄(최대 200자)만 쓰면 된다. |
| 혼자 쓰는 일기에는 반응이 없어 허전하다 | 감정 이름과 강도, 공감 메시지를 바로 돌려준다. |
| 힘든 마음을 일기에 털어놓았을 때 아무 도움 없이 지나간다 | 위기 표현이 있으면 공감 메시지와 함께 전문 상담 연락처를 먼저 보여 준다. |
| 개인적인 기록이 남에게 보일까 걱정된다 | 로그인한 사용자는 자기 일기만 볼 수 있고, 원하면 자기 일기를 지울 수 있다. |

### 1.4 제품 원칙

- 화면은 종이 일기장처럼 따뜻하고 편안하게 만든다.
- 이 앱은 의료 서비스가 아니다. 진단하거나 치료 조언을 하지 않고, 위기 상황에서는 전문 상담 기관으로 이어 준다.
- AI가 실패해도 일기 저장과 위기 안내는 멈추지 않는다.

## 2. 목표와 성공 기준

### 2.1 목표

1. 구글 로그인 사용자가 한 줄 일기를 쓰고 감정 분석과 공감 메시지를 받는다.
2. 위기 표현이 있으면 AI 상태와 상관없이 상담 연락처를 안내한다.
3. 사용자의 일기는 본인만 볼 수 있고, 본인만 지울 수 있다.
4. 로컬에서 끝까지 동작한 뒤, GitHub 저장소 `ai-empathy-diary-ch7`에 올리고 Vercel에 배포한다.

### 2.2 성공 기준

아래 수치는 사용자가 승인해 확정되었다. 4단계(QA)에서 이 표대로 측정한다.

| # | 지표 | 목표 | 측정 방법 |
|---|---|---|---|
| S1 | 일기 저장 후 공감 메시지가 화면에 나오기까지 걸리는 시간 | 1순위 모델이 정상일 때 **10초 이내**(시험 10회 중 8회 이상). 2순위로 넘어간 경우도 **45초 이내**에 결과나 기본 위로 문구가 나온다. (모델별 대기 시간 20초 × 2 + 여유. 근거는 `docs/PLAN.md` 2-B) | 로컬과 배포 주소에서 저장 버튼을 누른 시점부터 결과 카드가 보일 때까지 시간을 잰다. |
| S2 | 위기 시험 문장 감지율 (서버 키워드 검사 단독) | 위기 시험 문장 **20개 이상**에서 **100%** 감지 | 4단계에서 qa-engineer가 문장 목록을 만들어 자동 테스트와 화면에서 확인한다. |
| S3 | 위기 시험 문장 감지율 (키워드 검사 + AI 판단, 두 겹) | **100%**. AI를 일부러 실패시켜도 S2 결과가 유지된다. | 같은 문장 목록으로 확인. AI 실패 상황은 키 값을 틀리게 바꾼 셸에서 시험한다. |
| S4 | 평범한 문장에서 위기 안내가 잘못 뜨는 비율 | 일상 문장 **20개 이상** 시험 결과를 기록한다. 관용 표현(예: "죽을 만큼 맛있었다")은 결과를 기록하고 사용자와 기준을 정한다. | 4단계 점검 목록 5번 |
| S5 | AI 실패 시 일기 저장 성공률 | **100%**. 두 모델이 모두 실패해도 일기는 저장되고 기본 위로 문구가 나온다. | 키를 틀린 값으로 바꾼 상태에서 일기 10건 저장 |
| S6 | 다른 사용자 일기 노출·삭제 | **0건**. 로그인하지 않은 API 호출은 `401`, 남의 일기 id 조회·삭제는 `404`(남의 일기는 그대로 남음), 목록에는 내 일기만 나온다. | 4단계 권한 시험 |
| S7 | 비밀 값 노출 | **0건**. 네트워크 응답과 브라우저 번들에 `OPENROUTER_API_KEY`, `DATABASE_URL` 값이 없고, GitHub에 `.env`가 없다. | 3·4·5단계 점검 |
| S8 | 다른 스키마 보호 | `diary` 밖 스키마의 표 목록과 개수가 1단계 기록과 배포 후에 똑같다. | 1단계·5단계 조회 |
| S9 | 빌드와 테스트 | `npm run build`, `lint`, `test`가 모두 오류 없이 끝난다. | 3·4단계 |
| S10 | 핵심 흐름 | 구글 로그인 → 일기 쓰기 → 공감 메시지 → 지난 기록 보기 → (원하면) 일기 삭제가 로컬과 배포 주소에서 모두 동작한다. | 3단계, 5단계(사용자 직접 확인) |
| S11 | 무료 모델 안내 문구 노출 | 일기 쓰기 화면에서 **항상** 보인다(F3 완료 조건 8~10). | 4단계 화면 점검 |

## 3. 대상 사용자

| 유형 | 상황 | 필요한 것 |
|---|---|---|
| 일기를 가볍게 시작하고 싶은 사람 | 하루 끝에 짧게 기록하고 싶다. 길게 쓰기는 부담스럽다. | 한 줄만 써도 되는 입력, 쓰고 나면 반응이 오는 경험 |
| 위로가 필요한 사람 | 힘든 하루를 털어놓고 싶다. | 판단하지 않는 따뜻한 말, 필요할 때 바로 보이는 상담 연락처 |
| 자기 기록이 남에게 보일까 걱정하는 사람 | 개인적인 이야기를 쓴다. | 내 일기는 나만 본다는 확신, 지우고 싶을 때 지울 수 있는 수단 |

공통 전제: 구글 계정이 있고 한국어로 쓴다. (한국어 외 언어는 이번 범위 밖)

**특별히 조심할 사용자**: 위기 상황(자해, 극단적 선택 생각 등)에 있는 사용자가 이 앱에 마음을 털어놓을 수 있다. 이 경우 응답 속도, 문구, 연락처 안내의 정확성이 다른 어떤 기능보다 중요하다.

### 5.2 필수 기능

완료 조건은 모두 "예/아니오"로 확인할 수 있게 썼다. 4단계 QA가 이 조건을 하나씩 확인한다.

#### F1. 구글 로그인 (Auth.js) — 필수

- **설명**: 구글 계정으로 로그인한다. 로그인 처리는 Auth.js(`next-auth` v5)를 쓰고, 세션은 JWT 방식이다(DB 어댑터 없음). 일기의 `user_id`에는 구글 계정의 고유 ID를 쓴다. 필요한 환경 변수: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`. 세 값은 **아직 준비되지 않았다(확정, 열린 질문 1)**. 만드는 방법은 1단계에서 안내하고, 늦어도 3단계 로그인 시험 전까지 사용자가 준비한다.
- **완료 조건**
  1. 로그인하지 않은 사용자가 일기 쓰기·지난 기록 화면에 들어가면 로그인 화면으로 이동한다.
  2. 로그인 화면에 앱 소개 한 줄과 "구글로 시작하기" 버튼이 보인다.
  3. 구글 로그인에 성공하면 오늘의 일기 쓰기 화면으로 이동한다.
  4. 로그아웃하면 로그인 화면으로 돌아가고, 뒤로 가기를 눌러도 이전 일기가 보이지 않는다.
  5. 로그인하지 않고 `/api/entries`를 부르면 `401`이 돌아온다.
  6. 로그인 과정에서 `public` 등 `diary` 밖 스키마에 표가 생기지 않는다.
  7. 에이전트가 구글 비밀번호를 입력하지 않는다. 로그인 시험은 사용자가 직접 한다.

#### F2. 한 줄 일기 쓰기 — 필수

- **설명**: 한 줄 입력창에 오늘의 일기를 쓰고 저장한다. 저장하면 F3의 분석 결과까지 한 번에 돌려받는다. 최대 글자 수는 **200자(확정, 열린 질문 5)**다.
- **완료 조건**
  1. 빈 입력은 저장되지 않고, 안내 문구가 나온다.
  2. 공백이나 줄바꿈만 입력한 경우도 저장되지 않는다.
  3. 200자까지는 저장되고, 201자부터는 막히며 이유를 알려 준다.
  4. 입력창 근처에 현재 글자 수(예: 37/200)가 보인다.
  5. 같은 검사를 서버에서도 한다. 화면을 거치지 않고 API로 201자를 보내도 `400`이 돌아온다.
  6. 저장 중에는 저장 버튼이 중복으로 눌리지 않고 "분석 중" 표시가 나온다.
  7. 이모지와 줄바꿈이 들어간 글도 저장되고 그대로 보인다.
  8. `<script>` 같은 HTML 문자열을 써도 화면에서 실행되지 않고 글자 그대로 보인다.
  9. AI 분석이 실패해도 일기는 저장된다.
  10. 하루에 몇 번 쓰는지는 제한하지 않는다. (`docs/PLAN.md`에 제한이 없다.)

#### F3. 감정 분석과 공감 메시지 — 필수

- **설명**: 저장한 일기를 AI(OpenRouter)가 읽고 감정 이름, 강도, 공감 메시지를 만든다. 1순위 `nvidia/nemotron-3-ultra-550b-a55b:free`가 실패하면 2순위 `nvidia/nemotron-3.5-super-vl:free`를 쓴다. 필요한 환경 변수: `OPENROUTER_API_KEY`(서버에서만 사용). 무료 모델은 제공자가 입력을 기록하거나 학습에 쓸 수 있다. **사용자는 이를 받아들이기로 했고, 화면에 안내하기로 했다(확정, 열린 질문 4).**
- **감정 분류 목록 (확정, 열린 질문 5)**
  - **기쁨, 슬픔, 분노, 불안, 평온** 5개.
  - AI는 이 목록 안의 이름 **하나**만 고르게 한다. 목록에 없는 이름이 오면 분석 실패로 보고 2순위로 넘어간다.
  - 외로움, 피로, 설렘, 감사 등 다른 감정은 이번 범위에 넣지 않는다. (6번 범위 밖 항목)
- **감정 강도 (확정)**: 1~5의 정수(1 약함, 5 강함). DB에는 정수(`emotion_score`)로 저장한다.
- **공감 메시지 기준 (확정)**
  | 항목 | 기준 |
  |---|---|
  | 언어·말투 | 한국어, 부드러운 존댓말(해요체). 예: "~했군요", "~이었겠어요" |
  | 길이 | **2~4문장**, 전체 약 **200자 이내** |
  | 내용 순서 | ① 쓴 내용과 감정을 알아주기 → ② 위로·응원 한마디 |
  | 하지 않을 것 | 판단·훈계·충고, 진단, 의학적 조언, 일기에 없는 사실 지어내기, 과장된 칭찬 |
  | 표현 | 이모지는 쓰지 않는다. 일기 속 문장이 AI 지시처럼 작동하지 않는다(프롬프트 인젝션 방지). |
  | 위기일 때 | 더 조심스럽게: 가볍게 넘기지 않고, 마음을 알아주며, 혼자가 아니라고 전하고, 상담 연락처를 보게 이끈다. 밝은 응원 문구는 쓰지 않는다. |
- **무료 모델 안내 문구 (확정)**

  > 이 앱은 무료 AI 모델을 사용해요. 모델 제공자가 입력한 내용을 기록하거나 학습에 사용할 수 있으니, 개인정보나 민감한 정보는 적지 않는 것이 좋아요.

- **기본 위로 문구 (확정, 분석 실패 시)**: "오늘의 마음을 한 줄로 남겨 주셔서 고마워요. 지금은 분석이 어려웠지만, 일기는 안전하게 저장했어요. 오늘도 수고 많으셨어요."
- **완료 조건**
  1. 저장하면 감정 이름, 강도, 공감 메시지가 결과 카드로 보인다.
  2. 감정 이름은 기쁨·슬픔·분노·불안·평온 5개 중 하나다.
  3. 공감 메시지는 2~4문장이고 한국어다.
  4. 1순위 모델이 시간 초과·오류·이상한 응답이면 2순위 모델이 쓰이고, 실제로 쓰인 모델 이름이 저장된다(`model_used`).
  5. 두 모델이 모두 실패하면 오류 화면이 아니라 **기본 위로 문구**가 나오고, 일기는 저장된다.
  6. 결과 카드가 나타나면 스크린 리더가 읽는다(`aria-live`).
  7. 브라우저 네트워크 응답과 번들에 `OPENROUTER_API_KEY` 값이 없다.
  8. **무료 모델 안내 문구가 "오늘의 일기 쓰기" 화면의 입력창 바로 아래에 보인다.** 일기를 쓰기 전, 저장 버튼을 누르기 전에 읽을 수 있는 위치다. (위치의 세부 모양은 frontend-developer가 정하되, 저장 버튼보다 위에 있어야 한다.)
  9. 안내 문구는 접거나 닫을 수 없고, 로그인할 때마다 항상 보인다. 저장 결과 카드가 나온 뒤에도 사라지지 않는다.
  10. 모바일 폭(375px)에서도 스크롤 없이 입력창과 함께, 또는 입력창 바로 아래에서 보이며, 글자가 잘리지 않는다.
  11. 안내 문구는 본문 글자 대비 기준을 지켜 읽기 쉽고, 스크린 리더가 입력창 설명으로 함께 읽는다(예: `aria-describedby`).
  12. 안내 문구가 위기 안내 상자(F5)를 가리거나 밀어내지 않는다. 위기 안내 상자가 나오면 상자가 공감 메시지 위에 있고, 안내 문구는 입력창 아래에 그대로 있다.

#### F4. 지난 기록 보기 — 필수

- **설명**: 내가 쓴 일기를 최신순으로 보고, 날짜와 감정을 함께 확인한다.
- **완료 조건**
  1. 일기가 날짜별로, 최신순으로 나열된다.
  2. 각 항목에 날짜, 일기 내용, 감정 표시가 보인다.
  3. 항목을 열면 공감 메시지도 볼 수 있다. (공감 메시지를 목록에 바로 보일지 상세에서 보일지는 화면 담당이 정하되, 공감 메시지를 볼 수 있어야 한다.)
  4. 기록이 많으면 일정 개수씩 나눠 보이고 "더 보기"로 다음 기록을 불러온다.
  5. 기록이 하나도 없으면 안내 문구가 나온다.
  6. 불러오는 중, 불러오기 실패 상태가 각각 구분되어 보인다.
  7. 분석에 실패한 일기도 목록에 나온다. 감정은 "분석 안 됨"으로 표시한다.
  8. 새로 쓴 일기가 새로고침 없이, 또는 다음 방문 때 목록 맨 위에 나타난다.

#### F5. 위기 표현 시 상담 연락처 안내 — 필수

- **설명**: 일기에 자해, 극단적 선택 같은 위기 표현이 있으면 공감 메시지와 함께 상담 연락처를 보여 준다. 감지는 두 겹이다. 서버의 키워드 규칙 검사와 AI의 판단 중 **하나라도** 위기로 보면 안내한다. AI가 두 모델 모두 실패해도 키워드 검사와 연락처 안내는 동작한다.
- **감지 대상 표현 예시**: 자해, 자살, 죽고 싶, 극단적 선택, 사라지고 싶 등 (최종 목록은 ai-integration-specialist가 정하고 4단계에서 검증)
- **위기 안내 문구 (확정, 사용자 확인 완료 — 열린 질문 6)**

  > 지금 많이 힘드셨군요. 이런 마음을 털어놓아 주셔서 고마워요. 혼자 견디지 않으셔도 괜찮아요. 아래 전문 상담에서 지금 바로 이야기를 나눌 수 있어요. 당장 위험하다고 느껴지면 119에 연락해 주세요.

- **완료 조건**
  1. 위기 표현이 감지되면 공감 메시지 **위에** 상담 연락처 상자가 눈에 띄게 나온다.
  2. 상자에 위기 안내 문구와 연락처 4개(기관 이름, 번호)가 모두 보이고, 번호는 누르면 전화가 걸리는 링크(`tel:`)다.
  3. 상자는 자극적인 빨강을 쓰지 않고, 차분하지만 눈에 띄는 색과 크기로 보인다.
  4. 서버 키워드 검사만으로도 위기 안내가 나온다. 두 모델이 모두 실패하는 상태에서도 위기 문장을 쓰면 연락처가 나온다.
  5. AI만 위기로 판단한 경우에도 연락처가 나온다.
  6. 위기 여부가 DB에 저장되고(`is_crisis`), 지난 기록에서 그 일기를 열 때도 연락처 안내를 다시 볼 수 있다.
  7. 위기일 때 공감 메시지에는 밝은 응원 문구가 없다.
  8. 위기 시험 문장 감지율은 2.2의 S2·S3 목표를 만족한다.
  9. 화면과 서버 로그에 위기 일기 원문을 남기지 않는다.
  10. 관용 표현(예: "죽을 만큼 맛있었다")의 **최종 기준은 4단계에서 결과를 보고 사용자와 정한다.** 그 전까지의 방침(확정)은 놓치는 것보다 잘못 띄우는 쪽을 택하는 것이다.
  11. 위기 안내 상자 맨 아래에 "의료 서비스 아님" 한 줄 안내가 보인다.

#### F6. 내 일기만 보기 — 필수

- **설명**: 사용자는 자기 일기만 보고 쓰고 지울 수 있다. 모든 조회·저장·삭제는 서버에서 세션의 `user_id`로 제한한다. 요청 본문이나 주소로 받은 `user_id`는 믿지 않는다.
- **완료 조건**
  1. 로그인하지 않은 상태에서 일기 API를 부르면 `401`이 돌아온다.
  2. 다른 사용자의 일기 id로 조회하면 `404`가 돌아온다. (존재 여부를 알려 주지 않는다.)
  3. 일기 목록에는 로그인한 사용자의 일기만 나온다.
  4. 요청 본문에 다른 `user_id`를 넣어도 무시되고, 저장된 일기의 `user_id`는 세션의 계정 ID다.
  5. 모든 SQL은 매개변수 바인딩을 쓰고 `diary.` 접두어를 붙인다.
  6. DB 표는 `diary` 스키마 안에만 있고, 다른 스키마의 표는 바뀌지 않는다.
  7. 일기 삭제도 같은 규칙을 따른다. (F7 완료 조건 6~8)

#### F7. 일기 삭제 — 필수 (확정, 열린 질문 3)

- **설명**: 사용자가 자기 일기를 하나씩 지울 수 있다. 지운 일기는 DB에서도 완전히 없어진다(복구 기능 없음). 수정 기능은 이번 범위에 없다.
- **완료 조건**
  1. 지난 기록의 일기마다(또는 일기를 열었을 때) 삭제 버튼이 있다.
  2. 삭제 버튼을 누르면 바로 지워지지 않고, 먼저 확인을 받는다. 확인 문구 예: "이 일기를 지울까요? 지우면 되돌릴 수 없어요." 확인(지우기)과 취소 버튼이 있고, 취소하면 일기는 그대로 남는다.
  3. 지우기를 확인하면 일기가 새로고침 없이 지난 기록 목록에서 사라진다.
  4. 삭제 후 DB의 `diary.entries`에서 그 일기의 행이 없다. (숨김 표시가 아니라 실제 삭제다.)
  5. 삭제한 일기의 id로 다시 조회하거나 다시 삭제하면 `404`가 돌아온다.
  6. 로그인하지 않고 삭제 API를 부르면 `401`이 돌아온다.
  7. 다른 사용자의 일기 id로 삭제를 요청하면 `404`가 돌아오고, 그 일기는 지워지지 않고 그대로 남는다.
  8. 서버는 삭제 조건에 세션의 `user_id`를 붙인다. 요청 본문이나 주소에 다른 `user_id`를 넣어도 무시된다. SQL은 매개변수 바인딩을 쓰고 `diary.` 접두어를 붙이며, `diary` 밖 스키마는 바뀌지 않는다.
  9. 삭제가 실패하면(네트워크·서버 오류) 일기는 목록에 그대로 남고, 실패했다는 안내가 나온다. 처리 중에는 지우기 버튼이 중복으로 눌리지 않는다.
  10. 위기로 표시된 일기와 분석에 실패한 일기도 똑같이 지울 수 있다.
  11. 확인 창은 키보드만으로 열고, 선택하고, 닫을 수 있다. 창이 열리면 포커스가 창 안으로 옮겨지고, 스크린 리더가 확인 문구를 읽는다. 닫으면 포커스가 원래 자리로 돌아온다.
  12. 서버 로그에 삭제한 일기의 원문을 남기지 않는다.
